# Dev-машины и CI/CD — план встречи

**Запрос с ретро 28.08:** рассказать команде, что крутится на dev-машинах и как устроена инфраструктура.

Снимок Docker: **2026-09-09**. Контейнеры на `.234` приходят и уходят (НИОКР + CI-джобы) — список не догма.

## Цель

Дать команде общую картину: что развёрнуто на dev, как связаны CI/CD, окружения и типовой цикл разработки.

## Правила, которые нужно сказать вслух

1. **`.234` (Dev)** — рабочая РТУ + Docker-песочница. Сюда **можно** подкладывать сервисы под НИОКР. Не убивать чужие контейнеры «на глаз»: рядом крутятся чужие стенды и эфемерные CI-джобы.
2. **`.235` (Stage)** — РТУ, которую **обновляет QA**. Сюда **ничего не подкладываем**. Если версия старая / сервис лежит — **просить обновление**, не чинить руками.
3. **CI ≠ одна тачка.** Основные MR-джобы — на **Astra Linux**. Часть джоб — на `.217` (CI/CD) и `.212` (крабовая). На `.234` тоже всплывают GitLab runner-контейнеры.
4. **Sentry** живёт на `.217` вместе с CI/CD.

## 2. CI/CD

Картина для рассказа (без претензии на полный `.gitlab-ci.yml` каждого репо):

```
MR / pipeline
    ├─ основная масса job  →  Astra Linux (раннер)
    ├─ часть job            →  192.168.232.217 (CI/CD-хост)
    ├─ часть job            →  192.168.232.212 (крабовая)
    └─ иногда job           →  192.168.232.234 (видно runner-контейнеры)
Артефакты / образ          →  registry (GitLab)
Ошибки в рантайме          →  Sentry на .217
Стенды                     →  .234 (Dev/НИОКР)  |  .235 (Stage/QA)
```

**Что сказать по пайплайну (типовой фронт):** lint/test → build → (иногда) Docker image → деплой на стенд **не всегда автоматический**. Для веб-клиента отдельно (созвон AQA 09.09): job публикации образа ещё дописываем; подъём контейнера на стенде AQA — через **dind**, раннер выделяет AQA.

## 3. Окружения

| Окружение           | Где                              | Кто деплоит / обновляет                                                | Для чего                                         |
| ------------------- | -------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------ |
| **Dev / НИОКР**     | `.234` + Docker на той же машине | Команда (сами) + иногда CI                                             | Фичи, две линии веб-клиента, либы, DevProc, демо |
| **Stage**           | `.235`                           | **QA** обновляет РТУ; фронты — по договорённости, без самодеятельности | Проверка «как у QA», без мусора                  |
| **AQA / автотесты** | отдельный стенд (dind, в работе) | AQA + будущая CI job                                                   | Автотесты веб-клиента                            |
| **Прод / клиент**   | не эти машины                    | релиз по тегу / пакет                                                  | Не путать с `.234`/`.235`                        |

**Dev vs Stage одним предложением:** на `.234` можно экспериментировать; `.235` — эталон «не трогать руками».

## 4. Типовые сценарии (2–3 живых примера)

### A. MR фронта (веб-клиент / пульт / МОА)

1. Открыл MR → CI уходит **в основном на Astra**.
2. Если пайплайн зелёный — ревью → merge.
3. Проверка на железе: поднять/обновить контейнер на **`.234`**, не на `.235`.
4. Если нужна проверка «как у QA» — **попросить QA обновить `.235`**, не `docker restart` на Stage.

### B. НИОКР на живой РТУ

1. Нужна РТУ с кастомным веб-клиентом / админкой / моком — только **`.234`**.
2. Имя контейнера осмысленное (`rtu-web-client-support-branch`, не `boring_leakey`).
3. Порт не пересекать с занятыми (`9900/9901/9904`, `9985/9986`, `9995/9996`, `3335/3336/3340`, `3001`).

### C. «Почему у QA другое»

1. Stage обновляет QA, не мы.
2. На `.235` сейчас **нет** support-ветки веб-клиента и dealing-admin — сравнивать с Dev нельзя 1-в-1.
3. Если на Stage лежит сервис (сейчас: `dealing-console` / `dealing-console-ui` в restart loop) — эскалация в QA, не «починить на Stage как на Dev».

## 5. FAQ / боли

| Боль | Что отвечать / что делать |
|---|---|
| «Задеплоил на Stage, ничего не встаёт» | Так и задумано: Stage не наша песочница. Просить QA. |
| «На Stage крутится старый веб» | Следить и **просить обновление**, не подкладывать свой образ. |
| `dealing-console` / `dealing-console-ui` Restarting на `.235` | Зафиксировать на встрече; отдать QA (логи, с какого образа). |
| «Кто съел место/CPU на `.234`» | Смотреть `docker ps`: эфемерные runner/`npm ci` + чужие НИОКР. Не `docker rm -a`. |
| «Где Sentry?» | `192.168.232.217`. |
| «Почему CI красный, хотя локально ок» | Сначала Astra-раннер (ОС/зависимости). Потом tags: не та машина (`.212` vs Astra). |
| «Где DevProc?» | Только Dev: `http://192.168.232.234:9986`. На Stage его нет. |
| «Где админка МОА / APS / Connect?» | Dev: `:9900` / `:9904` / `:9901`. Stage: `:9900` / `:9904` (Connect на Stage нет). |
| «Где dealing-admin?» | Только Dev `:9996` (БД `:9995`). |
